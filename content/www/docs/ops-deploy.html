Operação

Subindo o servidor com o denv

O repo é a aplicação: a stack vive em stacks/.celeros-hub/ (stack externa do denv), o conteúdo vai por rsync ao NFS e a API viaja numa imagem Docker versionada. Esta página é o roteiro completo — do zero ao dia a dia — com as pegadinhas que a prática já cobrou.

denv · Swarm Traefik websecure NFS rw registry: maikramer/celeros-hub

O mapa mental #

Toda mudança cai em um de três caminhos — saber escolher é 90% do deploy:

Do zero — primeira subida #

Uma vez por máquina/cluster. Pré-requisitos: o cluster Swarm com o Traefik (stack traefik) de pé e o NFS montado; Docker logado no registry; o repo clonado.

Registre a stack externa

O repo é a aplicação — o denv só precisa saber onde ela vive:

▸bash
denv external add ~/GitClones/CelerOS-Server

Crie os secrets de token

Sem eles o hub sobe, mas o /admin fica 503 (desabilitado por design). A partir da pasta env/ local (gitignored):

▸bash
python3 tools/make_tokens.py > env/tokens.json   # edite nomes/escopos
docker secret create celeros_hub_admin_token env/root-token.txt
docker secret create celeros_hub_tokens       env/tokens.json

Secrets são imutáveis no Swarm: rotacionar = docker secret rm + create + denv update (o hub relê o arquivo a cada request — sem restart do processo).

DNS & TLS (uma vez por domínio)

Na zona celer.tec.br do Cloudflare: registro os apontando para o IP público do Traefik (187.95.46.25). Proxied funciona com o Origin Cert existente; sem proxy, configure certresolver próprio. O entrypoint é o websecure — o container do hub não publica porta no host.

Sync + primeiro deploy

▸bash — tag = HUB_VERSION vigente em api/app.py
denv sync apply celeros-hub -y --no-tui      # conteúdo → NFS
denv update celeros-hub -t 0.7.0 --no-tui    # cria a stack (idempotente)

Na primeira vez o update cria a stack (create-or-update); nas seguintes ele só re-aplica. A imagem da tag sai do registry — se ela ainda não existir, faça o ciclo de código antes.

Confira

▸bash
curl -s os.celer.tec.br/health
# {"status":"ok","version":"0.7.0"}
denv status | grep celeros                # RUNNING 1/1

Conteúdo: sync #

Wiki, portal, help e o catálogo semeado vivem como arquivos no NFS — o hub lê do disco a cada request, então publicar conteúdo não toca no container:

▸bash
cd ~/GitClones/CelerOS-Server
# …edite content/… (wiki, portal, help), commit + push…
denv sync apply celeros-hub -y --no-tui

# conferindo o que iria antes (opcional):
denv sync diff celeros-hub
✓

O rsync não deleta o que só existe no servidor — apps publicados pela API admin em runtime (gravados no NFS pelo volume rw) sobrevivem ao sync. E o contrário também vale: remover um app do repo não o remove da loja; para isso use DELETE /admin/apps/<pkg>.

!

Mudou CSS/JS do portal ou da wiki? O Cloudflare cacheia assets estáticos (o mount não manda no-cache para eles). Convenção: cache-bust — bump na query da URL (/style.css?v=0703) no HTML que referencia. HTML e catálogos (/store/*.json, /api/info) são sempre frescos (cf-cache-status: DYNAMIC).

Código: o ciclo completo (com a dança do marker) #

Mudou api/app.py? O caminho tem 5 passos — e dois deles são o git-guard do denv conversando com você:

Suba a HUB_VERSION

Em stacks/.celeros-hub/api/app.py (ex.: 0.7.0 → 0.8.0). A tag da imagem é a versão do serviço — tag nova no registry força build de verdade; tag reescrita deixava o update pular o build e rodar código velho.

Commit + push do código

O git-guard do denv aborta sync/deploy com working tree sujo (“repo não está em dia”). Toda mudança de código entra commitada e pushed antes de chamar o denv.

Build + push da imagem

▸bash
denv build --service celeros-hub --tag 0.8.0 --push

Atenção: o build reescreve o marker ARG BASE_TAG em stacks/.celeros-hub/dockerfile.celeros-hub — o repo fica sujo de propósito (marcador da última imagem buildada).

Commit + push do marker

▸bash
git add stacks/.celeros-hub/dockerfile.celeros-hub
git commit -m "marker de build: ARG BASE_TAG=0.8.0" && git push

Sem isso, o denv update a seguir aborta no git-guard — a pegadinha clássica do fluxo (o próprio build suja o repo que o guard exige limpo).

Rolling update

▸bash
denv update celeros-hub -t 0.8.0 --no-tui

O update = sync + docker stack deploy in-place (nunca remove a stack, nunca dispara backup de boot). Container novo só quando imagem/config mudam de verdade; re-aplicar igual é no-op e o uptime preserva.

Verificação pós-deploy #

▸bash — 30 segundos de ritual
curl -s os.celer.tec.br/health | jq .          # versão nova?
curl -s os.celer.tec.br/api/info | jq '{uptime:.uptime_s, api:.firmware.api_level, apps:.store.apps}'
# uptime zerado = container rolou (imagem/config mudou)
# uptime preservado = no-op intencional (mesma tag, mesmo compose)

curl -s -o /dev/null -w '%{http_code}\n' os.celer.tec.br/docs/     # o que mudou, no ar?
denv status | grep celeros-hub                  # RUNNING 1/1

O healthcheck do Swarm bate /health a cada 30 s (start period 30 s); o painel do denv consome /health + /api/info como JSON de monitoramento.

Rodar local (dev) #

▸bash
pip install fastapi==0.115.12 "uvicorn[standard]==0.34.2" python-multipart==0.0.20

BASE_URL=http://127.0.0.1:8901 CONTENT_DIR=$PWD/content \
HUB_ADMIN_TOKEN=devtoken HUB_DOCS=1 \
  python3 -m uvicorn --app-dir stacks/.celeros-hub/api app:app --port 8901

# Swagger em http://127.0.0.1:8901/api/docs (HUB_DOCS=1)

Nota: help e OTA usam URLs absolutas de produção nos arquivos de conteúdo — para testar local, mapeie os.celer.tec.br para 127.0.0.1 no /etc/hosts ou aponte o BASE_URL de teste. Antes de qualquer deploy de código: python3 tools/test_api.py (67 checks offline, sem rede e sem secrets).

Troubleshooting — os reais #

SintomaCausa / caminho
update aborta: “repo não está em dia”git-guard: working tree sujo — quase sempre o marker BASE_TAG que o próprio build reescreveu. Commit + push do marker e rode de novo (ou --no-git-check consciente)
mudança no CSS/JS não aparececache do Cloudflare em asset estático — bump na query ?v= da URL no HTML
uptime não zerou após updateimagem/compose idênticos → Swarm não reinicia (no-op). Se esperava rollover, confira se a tag e o compose mudaram de verdade

portal 404 / wiki não aparecerodou o denv sync apply? arquivo está em content/www/…?
/admin devolve 503nenhum secret de token montado — esperado até configurar
app publicado “sumiu” após syncnão some: sync não deleta runtime; pacote sem app.json+main.js é pulado do catálogo
downloads zeraram após redeploycontador vive em /data/stats na camada do container — conhecido, sem volume dedicado ainda
