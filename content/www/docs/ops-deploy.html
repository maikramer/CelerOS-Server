Deploy & ops

O repo é a aplicação: a stack vive em stacks/.celeros-hub/ (stack externa do denv) e o conteúdo em content/ sincroniza por rsync para o NFS. Duas alavancas: sync (conteúdo, sem restart) e build/update (código da API, por tag de versão).

denv · Swarm Traefik websecure NFS rw

Anatomia da stack #

ArquivoPapel
service.ymlmetadados da stack denv, healthcheck /health, monitoring (/health + /api/info), registry maikramer/celeros-hub e a definição do sync (rsync content/ → NFS, required_dirs content+audit)
docker-compose.ymlserviço único: imagem por BASE_TAG, secrets montados, volumes NFS rw (content + audit), healthcheck wget, placement no nó dockergpu, Traefik Host(os.celer.tec.br) na rede pública, limites 0.5 CPU / 256 MB

env/ gitignoredroot-token.txt, tokens.json e env.sh — fonte local dos Docker secrets

Registro único na máquina de dev: denv external add ~/GitClones/CelerOS-Server.

Mudou conteúdo? Sync. #

Wiki, portal, help, apps publicados por API admin — tudo isso vive no NFS como arquivos. O fluxo do repo para o servidor é um rsync:

▸bash
# conteúdo novo no repo (ex.: esta wiki) → servidor:
denv sync celeros-hub          # rsync content/ → /mnt/nfs/celeros-hub/content

# sem restart, sem rebuild: o hub lê do disco a cada request
✓

O sentido inverso acontece sozinho na publicação por API: o admin grava no NFS (volume rw). O rsync do sync não deleta o que só existe lá (apps publicados em runtime sobrevivem).

Mudou a API? Build + update por tag #

▸bash
# 1) suba HUB_VERSION em api/app.py (ex.: 0.7.0) — a TAG é a versão do serviço
#    (git-guard: commit + push antes de deployar)

# 2) build + push da imagem com a tag nova
denv build --service celeros-hub --tag 0.7.0 --push

# 3) rolling update
denv update celeros-hub -t 0.7.0

Tag inexistente no registry força build de verdade — o motivo da convenção "tag = versão": tag reescrita deixava o update pular o build e rodar código velho.

Secrets #

▸bash — a partir da pasta env/ local
docker secret create celeros_hub_admin_token env/root-token.txt
docker secret create celeros_hub_tokens       env/tokens.json
# (secret já existe? docker secret rm antes — são imutáveis)

O compose mapeia para HUB_ADMIN_TOKEN_FILE / HUB_TOKENS_FILE; o hub relê os tokens a cada request (detalhes em segurança).

DNS & TLS (uma vez) #

  • Zona celer.tec.br no Cloudflare: os → IP público do Traefik (187.95.46.25), proxied funciona com o Origin Cert existente.
  • Sem proxy: entre com certresolver próprio ou Origin Cert do host.
  • O Traefik publica websecure; o container do hub não tem porta no host.

Rodar local (dev) #

▸bash
pip install fastapi==0.115.12 "uvicorn[standard]==0.34.2" python-multipart==0.0.20

BASE_URL=http://127.0.0.1:8901 CONTENT_DIR=$PWD/content \
HUB_ADMIN_TOKEN=devtoken HUB_DOCS=1 \
  python3 -m uvicorn --app-dir stacks/.celeros-hub/api app:app --port 8901

# Swagger em http://127.0.0.1:8901/api/docs (HUB_DOCS=1)

Nota: help e OTA usam URLs absolutas de produção nos arquivos de conteúdo — para testar local, mapeie os.celer.tec.br para 127.0.0.1 no /etc/hosts ou aponte o BASE_URL de teste.

Testes #

▸bash — 67 checks offline
python3 tools/test_api.py
# … apps, multi-arquivo, limites, downloads, OTA (api_version/variant/anti-rollback)

Roda contra um TestClient com diretórios temporários — sem rede, sem secrets: válido para qualquer ambiente. É a mesma bateria que valida uma mudança de app.py antes do deploy.

No ar, como conferir #

▸bash
curl -s os.celer.tec.br/health          # {"status":"ok","version":"…"}
curl -s os.celer.tec.br/api/info | jq '{uptime:.uptime_s, apps:.store.apps, dl:.downloads_total}'

# no cluster:
docker service ls | grep celeros-hub     # REPLICAS 1/1
docker service logs celeros-hub --tail 50

O healthcheck do Swarm bate /health a cada 30 s (wget interno, start period 30 s); o painel do denv consome /health + /api/info como JSON.
