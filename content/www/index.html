O CelerOS

firmware 1.5

Sistema operacional com GUI e runtime de apps JavaScript para ESP32 — fork (GPL-3.0) do KryonOS, mantido pela Celer. O que roda no aparelho:

Apps em JavaScript

Apps ES5 rodam nativo no Duktape: canvas 240×320, toque, teclado na tela, armazenamento por app, timers e HTTP — API nível ….

IA no dispositivo

AI.chat() fala com DeepSeek e OpenRouter direto do firmware, com function calling — o modelo responde chamando funções do app. Chaves ficam fora do sandbox. O app Chat IA vem de série.

Voz e wake word

Mic.* grava WAV 16 kHz (com permissão) e o app Qwen é assistente push-to-talk. No cão robô, o detector “hi celer” roda na própria placa: “hi celer, senta”.

Phone Link

Integração com o Gadgetbridge: notificações, música, clima e chamadas chegam no relógio (Phone.*) — sem app proprietário no celular.

Watchfaces e Celer Link

Plugins watchface.js trocam o rosto do relógio sem reflashing, e o link BLE Celer Link conecta dois aparelhos com pareamento por código de 6 dígitos.

celerctl + SDK

Companheiro USB com debugger Duktape (breakpoints, watches), logcat, screencast do framebuffer, emulador no PC, Flasher e o App SDK para desenvolver app no computador.

Código-fonte e documentação no repositório do CelerOS.

Para desenvolvedores

API …

Um app é uma pasta com app.json, main.js e (opcional) icon.png (PNG 64×64) — mais módulos .js e assets (.png .wav .json .bin, até 16 extras). Empacote e publique com a CLI do repo do hub:

# app (zip com app.json + main.js [+ icon.png] [+ extras])
python3 tools/publish_app.py minha-pasta-do-app \
  --hub https://os.celer.tec.br --token $CELER_HUB_TOKEN

# firmware OTA em um canal
python3 tools/publish_firmware.py esp32 build-cyd/CelerOS.bin \
  --version 1.5.0 --changelog "- novidade X" \
  --hub https://os.celer.tec.br --token $CELER_HUB_TOKEN

# canais: esp32 | smartdisplay_4848S040 | waveshare_amoled206 |
#         spotpear_zzpet | devkit      (default --api-version: a atual)

Contrato do app.json (API atual do sistema: …):

{
  "name": "Meu App",
  "packageName": "celeros.meuapp",
  "version": "1.0.0",            // suba a cada publicacao
  "author": "voce",
  "description": "sem acentos: a fonte do dispositivo nao tem.",
  "category": "Utilidades",
  "api": 6,                      // minimo de API do firmware p/ rodar
  "requires": [],                // "psram": libera main.js ate 128 KB
  "changelog": "1.0.0 - primeiro lancamento"
}

// campos gerenciados pelo hub (gravados no publish, nao edite):
// "size", "md5", "published_at", "publisher", "files"

Regras da loja: soma dos .js até 48 KB — 128 KB declarando "psram" em requires — cada arquivo acima de 30 KB precisa de api: 6 (firmware antigo truncava o download), icon.png até 16 KB e assets somando até 256 KB. Quem publica primeiro um packageName vira o dono — só o dono (ou o hub) atualiza/remove. Versão nova tem que ser maior que a publicada; republicar a mesma exige --force. O device valida o md5 de cada arquivo depois de baixar.

No OTA, o manifest pode declarar variant (ex.: smartdisplay-y8 para a SmartDisplay com relés — aparelhos com relé recusam manifest sem a própria variante; publique imagem de variante em canal próprio para não alcançar aparelho padrão) e api_version, validado pelo hub contra o nível atual.

Endpoints: GET /store/index.json · GET /store/all.json · GET /store/apps/<pkg>/main.js · GET /api/info · GET /health · POST /admin/apps · DELETE /admin/apps/<pkg> · POST /admin/updates/<canal> · DELETE /admin/updates/<canal> (admin: Authorization: Bearer <token> com escopo apps ou updates).
